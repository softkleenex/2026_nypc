## 확정 개선

**63 = 62 + HQ 구매 패딩 조건 수정** (`_extra = 300 if _hq_bypass else 0`
→ `... and not under_pressure`). 위협 지속 시 확장저축(300) 보호가 이미
무의미해졌는데(`hold=0`) HQ 즉시구매 패딩만 남아 HQ가 L1(훈련 1/턴)에
갇히는 구조적 함정을 수정. **econ 프록시 3개 독립 배치(시드1-40/41-80/
81-120, 총 240게임) = 90.4%** (62.py는 81.25%) — 통계적으로 확실. turtle/
rush/punch/샘플 전부 무회귀. 이중 감사 통과.

## 안전하지만 미검증인 추가분

**64 = 63 + anti-greed HQ 게이트**: AlphaBeta전 진단(상대가 HQ 투자 없이
순수확장, T54에 4기로 우리 기지 하나 각개격파) → 상대 HQ L1 고정+기지/
물량 열세 조건에서 우리도 HQ 저축 보류. `run_log_replay.py`로 그 정확한
상황을 재생하면 HQ 업글이 실제로 억제됨을 확인(메커니즘 검증됨). 그러나
프록시 4종 320게임에서 완전 무발동(no-op) — 트리거 조건이 우리 프록시엔
너무 희귀함.

**65 = 64 + 전방기지 2차방어 분산**: 갈치전 진단(T29/42/60에 서로 다른
기지 3개를 순차로 각개격파당해 T75부터 0기지로 114턴 방치) → `defend_at`
가 기지 하나만 지정하던 걸 2순위 위협 기지에도 1기 배분. 역시 프록시
320게임 전부 무발동.

**공통점**: 64/65 둘 다 "정교한 다중 타이밍/다중 목표 전술"을 겨냥하는데,
우리 프록시(econ/turtle/rush/punch)는 단순 매크로 스타일이라 이런 상황
자체를 안 만든다. 실전 검증은 다음 유저 평가에서만 가능.

- 전방보초 2홉 버전: 회귀(econ/turtle 둘 다 하락). 1홉으로 좁히니 no-op.

## 방법론 결론

**우리 프록시 4종의 행동 다양성이 한계에 도달했다.** 실전 손실의 다수가
"정교한 다중 타이밍/동시다발 전술"에서 오는데, 단순 매크로 스타일 프록시는
이런 상황을 재현하지 못해 관련 수정의 실전 가치를 프록시로는 검증 불가.

**추가 검증 시도(실패, 그러나 결정적)**: 갈치전의 순차 각개격파 패턴을
`opponents/proxy.py`에 `raider` 스타일로 직접 구현(적 기지 순차 습격,
15턴마다 목표 갱신) 후 강화(hq_cap=5, target_bases=9)까지 했으나 **64.py·
65.py 둘 다 60/60 완승** — 스크립트로 빠르게 만든 프록시로는 우리 봇의
누적된 매크로 강함을 절대 못 뚫는다. 이는 "프록시로 상위권 격차를 재현할
수 없다"는 걸 반증이 아니라 **실증**한 결과다: 실전 2100+급 상대의 강함은
특정 전술 하나가 아니라 200턴 전체에 걸친 수많은 작은 실행 우위의 누적이라,
단기간에 만든 스크립트로는 흉내조차 안 난다.

## 2라운드 (계속 진행, /goal 세션 고정 이후)

  안전하니 유지.

  "과거 기지 레벨업 공격적 시도는 econ 5승->0승으로 기각됨"이라고 명시돼
  있어 손대지 않음 — 기존 경고를 무시하지 않는 게 중요.

- **repair_turn 184→170 (기각)**: 4개 프록시 전부 완전 무변화.

- **좌우 대칭 검증**: 66.py 미러 자가대결 100게임 → 98무1승1패(같은 시드

- **half_ratio 1.0→1.15 (기각)**: econ 90%(소폭 개선, -1패) vs **rush

  다른쪽 회귀" 패턴이 반복되는 것 자체가 진짜 평탄지대(파레토 경계)에
  있다는 신호.

- **supply_fund UPKEEP 계수 누락 (기각, 흥미로운 반례)**: `alive*(200-turn)`
  공식에 UPKEEP(턴당 2골드/유닛)이 곱해져 있지 않아 종반 소규모 병력에서
  필요액의 절반만 예비하는 진짜 산술 오류를 발견. 수정 후 테스트하니
  1차 배치는 무변화(단 평균 턴수는 처음으로 실제 변화 -- 발동은 확인됨),
  2차 배치에서 turtle이 처음으로 78-0-2가 아니라 77-0-3으로 소폭 하락.
  "수학적으로 맞는" 수정이 실전에선 종반 훈련을 과하게 아껴 마무리 타이밍을
  놓치는 부작용 추정 — 순이득 불확실해 기각. **교훈: 코드상 산술 오류로
  보이는 것도 실측 없이 고치면 안 된다.**

**누적 결론**: 63(확실) 이후 64/65/66 네 가지 추가 가설 전부 "안전하지만
프록시로 증명 불가" 또는 "이론상 맞지만 실측 불확실"로 수렴. STYLES 파라미터 공간(garrison, expand_parallel,
repair_turn, advantage 임계값)도 전부 재확인 결과 평탄지대. 새로 만든
raider 프록시로 실전 격차 재현 시도도 실패(60/60 완승) — 프록시 검증
인프라 자체의 한계에 도달했다는 게 이제 여러 각도에서 확증됨.

## 3라운드: 병렬 워크플로우 (Codex+Claude 멀티에이전트)

사용자 제안으로 4개 렌즈(코드 버그 헌팅/전투 규칙 활용/타이밍 구조/Codex
외부 시각)가 병렬로 아이디어를 내고, 각자 가장 유망한 것 하나씩 직접
구현+4프록시 320게임 테스트까지 하는 워크플로우 실행. 순차 탐색보다 훨씬
효율적으로 새 각도를 찾아냄.

**채택 (bots/76.py = 66 + 4개 안전한 수정)**:
1. **invaders 오분류 수정**: 적 소유 건물에 정착한 워커까지 순수 거리
   기준으로 침공군 집계하던 것 수정 (미확보 지역 이동 중인 유닛만 침공군).
2. **강제출격 타이밍을 "대기시간" 기반으로**: `_pt+25`(절대턴) 대신 웨이브
   문턱 도달 시점부터 25턴 카운트. 전투 손실로 도달이 늦어지면 유예.
3. **기지 만렙 손상 수리 로직 추가**: HQ는 긴급수리가 있는데 레벨3(만렙)
   기지는 손상돼도 절대 수리 안 되던 진짜 빈틈. `BASE_REPAIR_COST` 상수가
   정의만 되고 어디서도 안 쓰이는 죽은 코드였던 게 증거.
4. **worker_slots 실제 인원 반영**: 빈 노동 슬롯까지 "소모됨"으로 계산해
   army_size를 과소평가하던 버그 수정 → push_army/big_idle 발동 지연 해소.

4개 전부 econ/turtle/rush/punch 각 80게임(양쪽) × 2배치(시드1-40, 41-80)
+ 샘플16 = 총 656게임에서 66.py 기준과 완전 동일(회귀 0). 실전 발동
가능성은 있으나(worker_slots·기지수리는 특히 그럴듯) 프록시로는 증명 불가.

**기각 (프록시 회귀 확인)**: harass squad 인원을 목표 포탑 레벨 기반으로
동적화 — econ 88.75%→85%, turtle 97.5%→91.25%로 뚜렷한 회귀. 즉시 폐기.

**중요한 방법론 교정**: 이 라운드에서 `bots/66.py`(무수정 원본)을 시드
41-80 turtle에서 재확인해보니 **77승0패3무(96.25%)가 이 시드 구간의
원래 기준선**이었음이 드러남 (이전 세션에서 "78-0-2가 항상 정상"이라고
전제한 게 틀렸음). 이 덕분에 2라운드에서 "turtle 소폭 하락"을 근거로
기각했던 **supply_fund UPKEEP 수정도 사실은 무죄**(같은 77-0-3)였다는
게 재확인됨 — 다만 econ에서 별도로 진짜 소폭 회귀(90%→88.75%)가 있어
최종 기각은 유지. **교훈: "기준값이 항상 같아야 한다"는 가정 자체를
매 시드 구간마다 직접 검증할 것 — 안 그러면 가짜 회귀로 좋은 수정을
잘못 버릴 수 있다.**
